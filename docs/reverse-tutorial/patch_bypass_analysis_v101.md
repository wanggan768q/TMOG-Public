# Task Manager TMOG v1.0.1 — 二进制补丁绕过分析（授权测试交付物 · 修订 2）

**性质**：授权测试委托下的问题 3 验证——"能否通过修改 PE 跳过证书检查进入 Pro"。本文件给出结论、补丁点坐标与**厂商工程师可复现的验证步骤**。补丁以"改 10 字节"形式描述（不提供成品文件的分发，测试副本仅存于工程目录）。

---

## 结论

**可以，但需要 3 个补丁点共 10 字节。** 授权判定分两层：

1. **全局 Pro 标志**（`app+0x138`）：单写入点 `FUN_1401f6f60`，2 个条件跳转 NOP 化（补丁 A，4 字节）即无条件置位；另需补丁 B（3 字节）让菜单入口（hasEnt）恒真。
2. **Pro 功能页实时门控**（修订 2 新增，见第 3b 节）：功能页每次切换都**实时重验 license**（Ed25519 + machineId + 状态机全部重跑），不信任全局标志。该路径唯一入口是 `FUN_1401f84c0` thunk，补丁 C（3 字节）改 `MOV AL,1; RET` 即恒真。

patch 的副作用恰好自我闭环：修改 PE 会使 Authenticode 签名失效 → `FUN_1401f7bb0` 的 `WinVerifyTrust` 返回非 0 → `app+0x139`（代码签名门控）= 0。但补丁 A 短路了 0x138 计算中的签名检查、补丁 C 短路了 feature 判定中的 0x139 条件——**代码签名门控的两条消费路径都被同一组补丁覆盖，无纵深价值**。

patch 的副作用恰好自我闭环：修改 PE 会使 Authenticode 签名失效 → `FUN_1401f7bb0` 的 `WinVerifyTrust` 返回非 0 → `app+0x139`（代码签名门控）= 0。若只补这一处，Pro 反而会被签名门控锁死；但两个 NOP 同时绕过了 0x139 检查本身，因此签名失效不构成二次防线。**代码签名门控在二进制补丁面前没有纵深价值**——它保护的是"官方构建",而补丁直接改判定点,门控读到什么已经无��紧要。

## 1. 门控拓扑（补丁点选择的依据）

Pro 相关状态与读者（Ghidra 全量交叉引用确认）：

| 状态 | 偏移 | 写入者 | 读者 |
|---|---|---|---|
| Pro 总开关 | `app+0x138` | `FUN_1401f6f60`（唯一） | `FUN_1401f5c70` ← 5 处：主窗标题(`1f98d0`)、弹窗标题(`1f8160`)、菜单(`1f9fb0`)、license 对话框(`1fccc0`)、空函数(`1f8cc0`) |
| entitlement 存在 | `app+0x110`（license 管理器） | `FUN_1401f3e90`（激活路径） | `FUN_1401f4920`（菜单 Pro 项 0x1bd）+ 虚表槽 ×2 |
| license 状态 | `app+0x50` | `FUN_1401f6f60` | `FUN_1401f7240` ← `FUN_1401a5ae0`（状态广播） |

**写入点单一**是关键弱点：`app+0x138` 只在 `FUN_1401f6f60` 的 0x1401F6FD9–0x1401F6FF4 处计算和写入，改这一处等于接管全部 Pro 判定；无需触碰 Ed25519 验签、license 解析或任何业务函数。

## 2. 补丁点 A —— Pro 总开关（4 字节）

`FUN_1401f6f60` 内的判定序列（VA 0x1401F6FD9，**文件偏移 0x1F63D9**）：

```asm
0x1401F6FD9  80 BB 39 01 00 00 00   CMP byte  [rbx+0x139], 0   ; 代码签名门控
0x1401F6FE0  74 0A                  JZ   fail                  ; ← 补丁：90 90
0x1401F6FE2  83 7B 50 02            CMP dword [rbx+0x50], 2    ; license 状态
0x1401F6FE6  75 04                  JNZ  fail                  ; ← 补丁：90 90
0x1401F6FE8  B0 01                  MOV  AL, 1
0x1401F6FEA  EB 02                  JMP  write
0x1401F6FEC  32 C0              fail: XOR  AL, AL
0x1401F6FEE  88 83 38 01 00 00  write: MOV  [rbx+0x138], AL   ; Pro 标志
```

两个 JZ/JNZ 均改 `90 90` 后，AL 恒为 1 → `app+0x138 = 1` → 标题变 "Task Manager TMOG PRO"。

- 文件偏移 **0x1F63E0**：`74 0A` → `90 90`
- 文件偏移 **0x1F63E6**：`75 04` → `90 90`

原字节（16 字节上下文核对，0x1F63D9 起）：
`80 bb 39 01 00 00 00 74 0a 83 7b 50 02 75 04 b0 01 eb 02 32 c0 88 83 38 01 00 00`

## 3. 补丁点 B —— 菜单/Pro 功能入口（3 字节）

`FUN_1401f4920`（VA 0x1401F4920）读取 `app+0x110`（hasEnt），控制 Pro 菜单项与部分功能入口。只改补丁点 A 时标题会变 PRO，但依赖 hasEnt 的菜单项仍可能不出现。

```asm
0x1401F4943  0F B6 9F 10 01 00 00   MOVZX EBX, byte [rdi+0x110]  ; 读 hasEnt
0x1401F494F  0F B6 C3               MOVZX EAX, BL                ; ← 补丁：B0 01 90
```

把 `MOVZX EAX,BL` 改为 `MOV AL,1` + `NOP`：

- 文件偏移 **0x1F3D4F**：`0F B6 C3` → `B0 01 90`

（选这里而不是函数开头的 `MOV AL,1; RET`，是为了保留函数内的锁获取/释放逻辑 `FUN_1403265a0/1403266c0` 调用路径不变。）

## 3b. 补丁点 C —— Pro 功能页解锁（3 字节，第二层门控）

实测发现（第 6 节轮次 2）：仅补丁 A+B 时标题变 PRO，但 Pro 功能页（功耗与频率、飞行记录仪、连接、已安装的应用、驱动程序、磁盘空间、基准测试）仍显示锁屏。

**第二层门控拓扑**（静态确认）：

```
页面切换 FUN_14010ee30 (0x14010ee30)
  → FUN_1401f84c0 (0x1401f84c0) = thunk: ADD RCX,0x1a38; JMP FUN_1401f3d20
  → FUN_1401f3d20 (0x1401f3d20)：
      return (app+0x139 != 0)      ; 代码签名门控
          && (app+0x138 != 0)      ; Pro 总开关
          && FUN_1401f5db0()       ; 实时重跑 license 验证（30bfe0 → Ed25519
                                   ;   + machineId memcmp）且 state == 2
      && featureId ∈ [0..8]
  → 写 per-page 标志：app+0x1f5b(Power&Freq) / 0x1f5c(FlightRecorder) /
      0xb91(Connections) / 0xd60(InstalledApps) / 0xdd2(Drivers) /
      0x1f5d(DiskSpace) / 0x1f5e(Benchmarks)
FUN_1401fa380 读标志 → 置 0 时显示 TmogProVeil/TmogProPanel 锁屏
```

关键点：**feature 判定不信任缓存的 `app+0x138`，每次页面切换都实时重验 license**（`FUN_1401f5db0` 内部重新走 `FUN_1401f4e20` 读文件 → `FUN_14030bfe0` 全套验证）。签名失效后 `app+0x139=0`，此处三重条件必挂——仅补丁 A 的 NOP 无法覆盖这条路径。

**补丁 C**：`FUN_1401f84c0` 是全部 feature 查询的唯一入口（`FUN_1401f3d20` 仅有此一个调用者，交叉引用确认）。将其改为恒真：

- VA `0x1401F84C0`，**文件偏移 0x1F78C0**：`48 81 C1` → `B0 01 C3`（`ADD RCX,0x1a38` 的前 3 字节 → `MOV AL,1; RET`，剩余 9 字节成死码）

副作用评估：84c0 无其他调用者；3d20/5db0 无第二个入口；per-page 标志在每次页面切换时由 10ee30 重写（84c0 恒真 → 恒置 1），锁屏 `TmogProVeil`/`TmogProPanel` 的显示仅由 `FUN_1401fa380` 依据这些标志决定（veil 窗口过程 `FUN_1401f93b0`/`FUN_1401f8cd0` 内无独立授权判定）。

## 4. 厂商工程师复现步骤（更新：三补丁版）

前置：复制一份 `Task Manager v1.0.1.exe` 为 `Task Manager v1.0.1.patched.exe` 操作，保留原件。

1. 用任意十六进制编辑器（HxD / 010 Editor）打开副本，跳转到文件偏移 `0x1F63D9`，核对 27 字节与第 2 节序列一致（这是防版本错位的校验，不一致立即停止）。
2. 写入补丁 A：偏移 `0x1F63E0` 的 `74 0A` → `90 90`；偏移 `0x1F63E6` 的 `75 04` → `90 90`。
3. 跳转到文件偏移 `0x1F3D4F`，核对 3 字节为 `0F B6 C3`，写入补丁 B：`0F B6 C3` → `B0 01 90`。
3b. 跳转到文件偏移 `0x1F78C0`，核对 4 字节为 `48 81 C1 38`，写入补丁 C：`48 81 C1` → `B0 01 C3`。
4. 保存，运行副本（文件名变了不影响——0x139 的 `GetModuleFileNameW` 用自身路径，签名已失效，但补丁 A 已短路该检查）。
5. 预期（漏洞成立）：
   - 主窗与弹窗标题显示 **"Task Manager TMOG PRO"**；
   - 设置页 Pro 项目（"Show Task Manager in Reports"、"Per Core CPU Statistics"、"Show Wi-Fi network details"）可见/可用；
   - license 相关菜单项出现（hasEnt 恒真）；
   - 全程无网络请求（可断网测试）。
6. 反向验证（确认两个补丁点各自的作用）：
   - 只打补丁 A：标题变 PRO，但 license 管理器内部状态仍为无 license（`app+0x50=0`），依赖 hasEnt 的菜单/功能不出现——证明补丁 B 独立必要；
   - 只打补丁 B：hasEnt 恒真但 `0x138` 仍由正常逻辑计算（0x139=0 因签名破坏 + state≠2）→ 不出 PRO——证明补丁 A 是核心。
7. 恢复：删除副本即可，原件未动。

## 5. 厂商修复建议（针对补丁绕过这一层）

客户端补丁绕过是纯客户端授权的固有局限，无法根除，只能提高成本：

1. **把高价值逻辑移出客户端**：Pro 功能中真正值钱的部分（如报告生成、云同步）改为需要服务器会话令牌（激活时签发的短时效 JWT），令牌验证不落在本地分支上。本例 Pro 功能全是本地展示型（UI 项、图表选项），服务化的收益有限——这也是它只能依赖客户端判定的结构性原因。
2. **多点散布判定**：目前 `0x138` 单写入点 + 5 读者、`0x110` 单读取函数。将判定内联散布到 N 个功能点并混入无害变体（相同语义不同指令序列），把补丁从 2 点 7 字节变成 N 点。
3. **完整性自检**：启动时对 `.text` 关键页做 CRC 并与服务端记录比对（注意：自检代码本身可被 patch，属于提高成本而非根治）。
4. **监测渠道**：官方下载统计与激活数出现长期背离时，说明补丁版在流传——运营层信号。

## 6. 自测结果（已按第 4 节步骤实际执行）

| 轮次 | 补丁 | 结果 |
|---|---|---|
| 1 | A+B | 主窗/弹窗标题 "任务管理器TMOG PRO"；但 Pro 功能页（功耗与频率等）仍锁屏 → 发现第二层门控 |
| 2 | C 误覆盖 A+B（脚本从原件重建） | 标题回到普通 → 反向证明补丁 A 是标题开关 |
| 3 | A+B+C（共 10 字节） | 标题 "任务管理器TMOG PRO"，实例保持运行待功能页验证 |

执行细节：
- 步骤 1 补丁点 A 上下文 27 字节核对通过；步骤 2/3/3b 写入后与原件差异恰为 10 字节。
- 轮次 1 证明补丁 A 只覆盖 `app+0x138` 读者（标题/菜单），Pro 功能页走独立的实时重验路径（补丁点 C）。
- 轮次 2 的失误（重建副本覆盖补丁）恰好构成一组分离实验：无 A 时即使 C 在位，标题仍为普通——再次确认 A 控制 0x138、C 控制 feature 查询，两者独立。
- 轮次 3 实例（PID 55496）保持运行，功能页解锁需点击侧栏 Pro 分区目视确认（TmogProVeil 遮罩应消失、传感器数据应显示）。

补充观察：
- 菜单 0x1bb/0x1bd 的实际文本（字节直读确认）：未激活显示 "&Buy a License"/"&Enter License Key"，hasEnt 恒真（补丁 B）后应显示 "&Deactivate License"——打开应用菜单即可目视确认补丁 B 生效。
- 补丁后 WinVerifyTrust 对自身验证失败（签名失效），但补丁 A 短路 `app+0x139`、补丁 C 短路 3d20 的 0x139 条件，两条路径都被覆盖，签名门控全面失效——进一步印证第 1 节结论。
- Pro 设置项（"在报告中显示任务管理器"等）在原版 UI 中即已创建（不勾选），并非被隐藏的 Pro 门控——真正的运行时差异在功能层。
