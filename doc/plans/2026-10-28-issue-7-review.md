## 3. 审查发现（不阻塞合同方向，属文档修正项）

**D1（中）：合同 §7 活跃窗口事件率低报 1-2 个数量级。** 合同写"活跃时（run12/13 窗口）瞬时数千事件/秒"；离线核算 run12=210265 事件、run13=229449 事件，会话窗口约 3s（300ms 预热+child<1s+2500ms 尾窗），即约 **7-9 万事件/秒**。这不改变"逐事件 O(1) 聚合"的设计结论，但会让维护者低估消费端负载与缓冲压力（MaximumBuffers=64 下每秒 8 万事件的丢失风险比"数千/秒"高得多）。同时研究文档 §8 "210K–229K 事件/2.5s 窗口"把整个会话总量算进 2.5s，两处口径都应修正。

**D2（中）：77824 数字链条存在 hdrPid/payloadPid 口径混用。** 合同 §2 与研究 §8 对 77824 的解释（"回显 65536 + server 侧读取块 12288"）是建立在 hdrPid=73356 桶上的——但 server 是父进程，其读取事件按 payloadPid 应归属父进程；12288=3×4096 出现在子进程的 hdrPid 桶里，恰是 hdrPid 张冠李戴的证据（该口径已被合同自己判定不可靠）。归档日志只按 `task|op|hdrPid` 与 `payloadPid` 两个维度聚合，**无法直接复现合同口径（payloadPid×opcode）下的 77824/65536 分解**——只能靠 bypid 总数 196608=3×65536 的自洽性间接验证。合同结论（op18 与 op11 重叠须排除）在两种口径下都成立，但引用数字的证据链条应注明口径。

**D3（轻-中）："hdrPid 恒 4"表述过强且 v1-v6 假阴性归因存疑。** 合同 §2 写"实测恒 4/宿主值"，但 run12/13 中多数事件 hdrPid 为真实 PID（仅部分=4 或错标值）。更关键的是：研究 §8 把 v1-v6"回环零事件"归因于"读 header PID 误判"——读法错误只会导致归属错误，**不会导致事件不产生**；run2 更是连背景流量都为 0（total events=0），说明 v1-v6 的零事件另有原因（消费就绪/参数差异）。归因不严谨不影响 v7 口径结论，但若真实原因是竞态/配置，同类问题可能在 #37 生产实现中复发——建议修正归因叙述并在 #37 中保留"消费者先就绪"防线（合同 §6 已含）。

**D4（轻）：op18-check 运行输出未归档。** 合同/研究声称对 op=18 做了归属验证（"TCP copy，与 op=11 重叠"），`op18-check.cpp`/`.exe` 在库，但其运行输出（payloadPid vs hdrPid 对照打印）不在 run1-13 归档中——该验证不可复查。建议补存输出或注明验证输出留存于会话记录。

**D5（轻）：研究 §8 样例解码行端口数值错误。** run13 事件 #1 `uddata=...ef2af7e9...` 样例解释写"10.53.1.54:10991→10.53.1.103:59895"；按网络序解码 ef2a=0xEF2A=61226、f7e9=0xF7E9=63465，与 10991/59895 不符（疑为字节序换算错误）。PID/size 解码正确（69688/1102）。"外部 mDNS 流量"定性亦存疑（mDNS 应为 5353 端口）。不影响布局结构结论（字段位置与长度正确），仅样例行需修正。

**D6（轻）：EventsLost>0 处理逻辑从未被触发验证。** 合同 §4/§6 的 `Unavailable-EtwLost` 标注语义按官方文档写入，run1-13 全部 EventsLost=0，§8.4 验收步骤（注入高速率流量触发丢失标注）从未演练成功过。建议在 §9 未实测表补充"丢失标注路径未实机触发"。

**D7（轻）：UDP `size` 口径未做已知量对照。** 合同 §2 表格 UDP 行引用"MOF + run13 外部流量"——外部流量无独立 ground truth（无已知实发量对照），"数据报载荷字节"对 UDP 是 MOF 推断+间接观察，精确性弱于 TCP 的 65536 对照。§9 未实测表未列此项，建议补充。

**D8（轻）：合同 §1 "MinimumBuffers 4–16" 与实测（探针固定 16）及 §7 "Min16=1MB" 表述不完全一致**；实现票需固定单一参数值，避免两处口径漂移。
