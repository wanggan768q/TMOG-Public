# PE 客户端授权逆向审计

对 Windows PE 的客户端授权机制做端到端审计：机制还原 → 门控测绘 → 补丁点提取 → 动态验证 → 厂商报告。方法论从 Task Manager TMOG v1.0.1 / v1.1.0 两轮实战提炼（教程：`F:\Work\txtest\Task Manager TMOG\REVERSE_TUTORIAL.md`，审计报告：同目录 `patch_bypass_analysis_v101.md` / `patch_bypass_analysis_v110.md`）。

## 前置检查（每次必做）

1. **授权确认**：用户未声明授权测试委托时，只做机制描述（网络协议、存储格式、验证架构），明确拒绝补丁点/绕过分析。已有委托才继续。
2. **环境**：确认 `GHIDRA_INSTALL_DIR` 指向 Ghidra 12.1.x 且 `rea --version` 可用。每个新终端先 export（PowerShell：`$env:GHIDRA_INSTALL_DIR = "..."`）。
3. **建快照**：第一个分析命令就是 `rea analyze <exe> --snapshot <name>.snapshot`，之后所有命令带 `--snapshot`（省掉每轮 8 分钟重分析；注意 read-bytes 不支持此参数）。

## 工作流（七个阶段）

### 阶段 0：版本身份核验（⚠️ 新版本回归必做第一步）

```powershell
Get-FileHash <exe> -Algorithm SHA256    # 与旧版哈希对比
python 直读文件长度/修改时间
```
- **哈希相同 = 重命名副本，直接套用旧版全部结论，到此为止**（v1.1.0 首次检测就踩过：文件同名实为旧副本，用户重新放置文件后才拿到真版）。
- 哈希不同才继续。另注意：文件可能在会话中途被用户替换，哈希异常时重新检查。

### 阶段 1：字符串侦察（⚠️ 编码陷阱）

```
rea search <exe> "license" --format md          # 宽泛词起步
rea search <exe> "<机制名词>" --format md        # 从命中列表提炼再精确搜
```
提取：服务器域名、UA、API 路径、存储文件名、RTTI 类名、错误文案。

**v1.1.0 教训：关键字符串可能整体改 UTF-16LE 存储**，ASCII 正则全落空 ≠ 字符串不存在。python 侦察必须双通道：

```python
ascii_ = re.finditer(rb'[\x20-\x7e]{5,}', data)
u16 = re.finditer(rb'(?:[\x20-\x7e]\x00){5,}', data)   # UTF-16LE
```

后续用 python 直读（`-I` 隔离模式 + 脚本落盘执行，here-string 里的中文路径会被转码损坏）。

### 阶段 2：存储与协议

- 已知 GUID、字段名常量：**python 解析 PE section 表直读字节**（VA↔offset 秒级 vs Ghidra 分钟级），模板见 REVERSE_TUTORIAL.md 阶段 5.1。
- rip 相对引用扫描（`48/4C 8D/8B` + mod=00 rm=101）用 python 在 .text 上全量做，比逐个 `rea xrefs` 快一个数量级。
- 产出：存储路径/格式、网络端点、请求/响应结构。

### 阶段 3：验证链（⚠️ 最大陷阱区）

- 解析点 callees 无 crypto API + 导入表无 `BCryptVerifySignature` **不能**证明无验签。
- 必须追输出数据的下游消费者（`rea xrefs`），验证可能藏在深处的静态链接库里。
- Ed25519 静态特征：0x40/0x20 长度检查、群阶 S 范围表、域常数表（sqrt(-1) 序列）、常数时间比较。跨版本定位：**把旧版的常数表字节（64B 片段）在新文件里 find**，秒级确认算法未变。
- **结论顺序铁律：POC 动态实测 → 再补静态证据。禁止静态推理直接下漏洞结论。**

### 阶段 4：门控拓扑

对每个关键标志做全量扫描。**字节模式扫描优于语义 xrefs**：

```python
# 对标志偏移（如 +0x138）扫 6 类模式：MOVZX r32,byte[reg+d32] / MOV r8,[reg+d32] /
# MOV imm8 / CMP imm8 / TEST imm8 / LEA/MOV 载入地址
```

按"写入点唯一+读者集中 → 补读者汇聚点"判定策略，产出三层表：标志 / 写入者 / 读者 / 策略。

- 警惕**双层门控**：全局标志 + 功能页实时重验是常见双保险，只补全局层会在功能页翻车。
- **读者经单一 getter（`return flag;` 单行函数）时，补 getter 一处接管全部读者**——比补写入点或读者更稳。

### 阶段 5：补丁点提取（⚠️ v1.1.0 核心教训）

- 从 `rea function` 的 `raw_result.value.assembly` 拿指令序列和 VA；python 做 VA→file offset。
- 每个补丁点记录：原字节（做断言用）/ 新字节 / 语义 / 副作用评估。
- **⚠️ 补丁点选"判定结果所有读者的必经汇聚点"，不是"验证流程内部的门"**：
  - ❌ 错误（v1.1.0 第一轮实测失败）：NOP 验证函数内部的判定跳转——该函数前置条件（license 验证）不通过时根本走不到这里。
  - ✓ 正确：单行 getter / 判定函数入口 `MOV AL,1; RET`（B0 01 C3）——输入无关、语义清晰、不碰验证过程。
- 函数入口改写用前 3 字节，核对原字节唯一性（`48 89 5C` 类序言多处出现，必须带函数地址断言）。

### 阶段 6：动态验证

- 补丁脚本**原子化**：每处先 assert 原字节再写入，一次性打全，最后统计 diff 字节数。
- 追加补丁从**上一次的副本**读入，禁止从原件重建（会静默覆盖）。
- 验证矩阵：标题/UI 差异、功能页点击、断网重测、**分离实验**（只打部分补丁验证各点独立性）。
- UI 自动化用 PowerShell：EnumWindows 精确取标题 → UIAutomation 枚举菜单/元素 → 截图像素采样检测锁屏蒙层。注意 InvokePattern 可能不支持，退回 SetCursorPos+mouse_event。
- **失败≠方法错**：功能页仍锁 → 找第二层门控（回阶段 4）。
- 验证完毕：停进程、删补丁副本（坐标存报告）、确认 `%LOCALAPPDATA%` 无 license 残留。

### 阶段 7：交付物

1. 机制审计报告（架构图 + 证据链 + evidence 文件索引 + 修复建议）
2. 补丁点坐标表（文件偏移 / 原字节 / 新字节 / 作用）
3. 厂商可复现步骤（含分离实验）
4. 方法论复盘（错误路线也写进去，标注为什么错）

## 报告红线

- 不分发成品补丁文件；坐标+步骤仅供委托方验证漏洞真实性。
- 所有结论标注 evidence 来源文件；未动态验证的结论必须标"待实测"。
- 测试残留（补丁副本、伪造 license）测完清理或明确告知位置。

## 新版本回归测试

用户说"新版本出来了要再测"时：

1. **阶段 0 哈希核验**：相同→旧副本，直接引用旧结论收工。
2. 旧补丁坐标原字节抽查（python 秒级）：全 MATCH→可能仍是同文件；MISMATCH→真新版。
3. 阶段 1 双编码字符串侦察：确认关键机制串（域名/文件名/JSON 字段/公钥）在新版的存在形态（可能换编码）。旧常数表字节 find 验证算法未变。
4. 建新快照（`tmog<ver>.snapshot`），旧地址全部作废，**按函数拓扑重新定位**（写入者→getter→读者链通常最稳）。
5. 补丁策略重推：先字节模式扫标志全量引用，再选汇聚点——**旧版策略不能照搬**（v1.0.1 的"NOP 写入点前判定门"在 v1.1.0 失效，v1.1.0 的正确点是 getter）。
6. 重跑阶段 6 验证矩阵 + 分离实验。

## REA CLI 实操注意（6.4.0）

- **REA 调用必须串行**——并行多个 `rea function` 会互抢 Ghidra 会话全部超时（v1.1.0 实测 4 并行全挂，串行 3-5 分钟/个正常）。
- 大函数（>1MB 反编译输出）可能超 330s 限时，报 `provider_timeout` 后重试一次通常成功（分析有缓存）。
- 所有中间产物落盘为 md 文件，命名 `f<addr后缀>.md`，结论必须可回溯。
